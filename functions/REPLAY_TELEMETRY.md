# 전투 재생 일별 집계

`submitMatchResult`는 통계 델타가 있는 정산 결과에만
`envs/{env}/replayTelemetryEvents/{eventId}`를 정산 트랜잭션 안에서 생성한다.
응답은 이 커밋까지 기다리며, 일별 집계 완료는 기다리지 않는다.
확정·플래그 처리뿐 아니라 재생 장애로 pending에 남은 호출의 unavailable 델타도 보존한다.
일반 대기, 이미 정산된 매치 재제출, HTTP 재생을 요청하는 중간 단계는 이벤트를 만들지 않는다.

`aggregateReplayDaily` 생성 트리거는 이벤트의 현재 문서를 다시 읽고,
기존 `telemetry/replayDaily/days/{day}` 카운터 증가와 이벤트 삭제를 한 트랜잭션에 커밋한다.
중복·동시 배달은 이벤트 문서의 존재 여부로 걸러 낸다. 이벤트 ID는 호출마다 새로 발급하며
정산 트랜잭션 재시도에서는 유지한다. 삭제된 ID를 다시 사용하지 않는다.
집계 날짜는 이벤트 생성 당시 UTC 날짜다. 배달이 늦어져도 처리 날짜로 바꾸지 않는다.

정산과 집계 이벤트의 생성이 원자적이므로 커밋 후 프로세스가 종료되어도 이벤트는 남는다.
집계 실패는 트리거로 전파해 재시도한다. 미처리 이벤트에는 TTL이 없으며 성공할 때만 삭제한다.
트리거 재시도 기간을 넘긴 장애는 운영 복구가 필요하다. 남은 이벤트의 `createdAt`과
트리거 오류 로그를 확인하고, 원인 해결 후 서버에서 `consumeReplayDaily`로 다시 처리할 수 있다.
재처리에서도 동일한 중복 방지 트랜잭션을 사용해야 한다.

## 배포 및 비용

- 최초 배포는 `aggregateReplayDaily` 트리거를 먼저 완료한 뒤 `submitMatchResult`를 배포한다.
  기존 생산자가 없는 상태에서 소비자를 먼저 준비해 생성 이벤트 누락을 피한다.
- 롤백 시에는 생산자를 먼저 되돌리고, 남은 이벤트 처리가 끝날 때까지 트리거를 유지한다.
- 일별 문서 경로와 필드는 유지되므로 조회 화면 변경이나 과거 데이터 이관은 필요 없다.
- 별도 통계 쓰기 왕복 1회를 응답 경로에서 제거한다. 기존 집계 쓰기에 더해 이벤트
  생성 1회·읽기 1회·삭제 1회와 트리거 실행 비용이 발생한다. 중복 배달·재시도 비용은 별도다.
- 일별 단일 문서의 경합 자체는 남는다. 이제 정산 응답과 분리되며, 카운터 분산은 적용하지 않았다.
