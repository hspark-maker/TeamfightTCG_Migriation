# OutGame (아웃게임/메타 레이어) 작업 규약

> 이 파일은 `Assets/Scripts/OutGame/` 작업 시 자동 로드되는 치트시트다.
> 상세 규약을 여기서 재정의하지 않는다 — **핵심만 요약 + 진실원 링크**. 이중 진실원 금지.

## 이 파트는

수집형 1vs1 카드배틀의 **아웃게임(메타) 레이어**: 세이브 · 재화 · 도감/소유 · 방치 생산 · 카드팩 · 보상.

- 성장 루프·Phase 로드맵 → `@docs/OutGamePlan/OUTGAME_ROADMAP.md`
- 승인·구조 기준 문서(진실원) → `@docs/OutGamePlan/STRUCTURE.md` (구조 변경 시 여기부터 갱신)

## 개발 방식 (빠른 반복 · 신입 2인)

- **1~2일 주기로 붙였다 검증**하는 속도가 최우선. 각 기능은 전체 부트 없이 **독립 E2E 검증 가능**하게 만든다.
  - 디버그 시간 점프(`GameClock`) · 인메모리 격리 · 옵션 `EnsureBoot`(아무 씬에서 테스트, 통합 시 no-op) 관용구 활용.
- 신입 2인(인게임/아웃게임) 협업 코드다. **추상화 수준은 확장 가능성에 맞춘다** — 확정 스펙이면 가장 단순하게, 컨텐츠 추가(카드종·팩종·재화종·보상종 등)가 예정돼 있으면 그 축만 열어둔다. 미래를 위한 과잉 추상화(YAGNI)도, 확장 예정을 무시한 하드코딩도 금지. 판단이 서지 않으면 플랜 단계에서 확장 가능성을 질문하고 답에 맞춰 정한다.

## 네이밍 (기술보다 개념)

- 클래스/메서드는 **게임 도메인 동사·명사**로. 기술 용어는 인프라 레이어에만.
  - 예: `CardPackOpener.TryPurchase`, `OwnershipManager.Grant`/`Revoke`, `CollectionProductionManager.Harvest`
  - 인프라 예외: `JsonFileRepository`, `IRepository`
- enum 접두사 `E` (`ECurrencyType`). 실패 가능 조회는 `Try*` + `out`.
- 필드 접두사: `s_`(static) · `m_`(인스턴스) · `t_`(지역) · `_`(파라미터).
  get-only 프로퍼티는 PascalCase, `[SerializeField]`는 camelCase.

## 코드 스타일

- **주석은 간략하게** — "왜"만 한 줄로. 코드가 곧 설명이면 주석을 달지 않는다. 불변식·비직관적 방어 로직·확장 축처럼 코드로 안 드러나는 의도만 남긴다. 장문 서술 금지.
- **클래스 내 멤버 순서: 위에서부터 필드/프로퍼티 → public 메서드 → private 메서드.** (읽는 사람이 공개 API를 먼저 보고, 세부 구현은 아래에서 찾게.)

## 아키텍처 3원칙 (SOLID를 단순하게)

1. **단일 창구**: 도메인 상태는 정확히 한 static 클래스만 소유하고, 세이브 슬롯 매핑도 그 클래스만 안다. 같은 목록/상태의 2번째 소유자를 만들지 말 것(마스터 데이터 드리프트 금지 — 카드 목록의 단일 창구는 `CardCatalog`).
2. **의존 방향 단방향**: `UI → 아웃게임 레이어 → Card(읽기 전용)`. 아웃게임에서 `Battle/`·`Network/`를 **참조·수정 금지**(반대 방향 `Battle → 범용 서비스(RewardService/CurrencyManager)`는 허용).
3. **추상화는 저장 매체(`IRepository`)에만**. 나머지는 SO setter 주입 + 미배선 fallback 관용구, UI 갱신은 `event Action …OnChanged`로 통지. 오케스트레이터(예: `CardPackOpener`)는 자체 영속 상태 없이 기존 매니저를 잇기만 한다.

## 세이브 3규칙 (핵심만)

1. 식별자는 **문자열 안정 키**(인덱스 금지 — 카드 추가돼도 진행도 안 밀림).
2. 스키마는 **필드 추가만**(변경·삭제·리네임 금지), `VERSION` 상수 필수, **로드 실패 시 진행도 0 덮어쓰기 금지**(corrupt 키에 백업).
3. 상태 변경 후 자기 매니저 `Save()` → `DataSaveManager.Save()`. 지연 flush이므로 **지급/차감 직후** Save 호출.

> 진실원: `OutGame/Save/{1.Repository,2.Domain,3.Manager}/` 각 파일 주석 + `docs/OutGamePlan/STRUCTURE.md`. 선례: `Assets/Scripts/Battle/DeckSaveManager.cs`.

## 플랜 단계 필수 질문 (답변으로 추상화 레벨을 정한다)

새 시스템/기능 설계 시, 구현 전 아래를 사용자에게 확인하고 답에 맞춰 구조를 결정한다:

- **확장 가능성은?** 이 컨텐츠가 앞으로 늘어나나(카드종·팩종·재화종·보상종·도감행 등)? 어느 축이 열려야 하고 어느 축은 고정인가 → **추상화 수준을 이 답으로 결정**(열린 축만 데이터/SO로 빼고, 고정 축은 단순하게).
- 이 상태의 **단일 소유 창구는?** 기존 매니저에 얹나, 새 static 창구가 필요한가?
- **세이브가 필요한가?** 필요하면 어느 도메인 값 객체(슬롯)에 붙이나 — 신규 슬롯인가?
- **기존 서비스로 충분한가?** (`CurrencyManager`/`OwnershipManager`/`CardCatalog`/`GameClock`) 새 추상화가 정말 필요한가?
- 이번 스코프에서 **E2E로 무엇을 어떻게 검증**하나(디버그 훅 포함)?
- **UI 배선·프리팹**은 이 태스크 범위인가, 문서화만인가?
