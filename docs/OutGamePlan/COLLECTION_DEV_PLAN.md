# 도감(Collection) 시스템 개발 플랜

> 각 구현 에이전트가 참조하는 **공유 브리핑**이다. 설계 확정본이 아니다 — 클래스 구성·시그니처·알고리즘은 여기서 정하지 말고 담당 에이전트가 판단한다.
> 기획 원본: `docs/OutGamePlan/COLLECTION_PLAN.md`.

## Context

`COLLECTION_PLAN.md`의 도감 기획을 실제 개발 플랜으로 옮긴다. 현재 프로젝트는 재화·세이브·카드 소유 등 **아웃게임 요소가 사실상 전무**하다(코드 조사 확인). 도감은 "카드를 모을 이유"와 "재접속할 이유"를 동시에 만드는 첫 아웃게임 루프이며, 이번엔 그 루프를 **독립적으로, 최소 토대**로 성립시키는 것이 목표다.

이 플랜은 상위 성장 루프 기획(대전→골드→카드팩→신규 카드셋→덱 강화)의 도감생산 단계에 해당한다. 상위 기획은 "단일 골드 범용 재화 서비스"와 카드팩 경제까지 포함하지만, **이번엔 도감이 필요한 만큼만 최소로 짓는다**(아래 스코프). 상위 계획과의 접점은 "지뢰"에 명시한다.

## 목표 (기획 — COLLECTION_PLAN.md 요약)

도감은 열람 화면이자 재화 생산 시설이다. 전체 카드 = 도감 1개, **3열 그리드 세로 스크롤 갤러리**. 스크롤에 쌓이는 단위는 **행(row)**, 행 하나가 곧 하나의 생산기다.

**효과 3종**
1. **재화 생산** — 행(3칸) 완성 시 생산기 활성. 쿨타임마다 생산, 상한 있음, 오프라인 누적 후 재접속해 수확.
2. **완성 보상** — 도감 전체 완성 시 1회성 보상.
3. **상세 열람** — 카드 클릭 → 상세 정보 팝업.

행 상태: **잠김(미완성) / 생산 중 / 수확 가능 / 상한 도달**. 행마다 독립적.

**★ 확장성 요구 (설계의 핵심 제약)**: 도감은 고정 크기가 아니다. 카드가 추가되면 개발자 개입 최소로 갤러리 칸·행·생산기·완성조건·진행도(`n/전체`)가 자동으로 따라오고, **기존 유저 세이브가 깨지지 않아야** 한다(수령한 완성보상·각 행 생산 진행도 유지). 3행은 현재 카드 9장의 결과일 뿐 상수가 아니다.

## 재사용 방침 (기존 코드베이스 — 신규 작성 금지)

- **전체 카드 열거**: `Assets/SO/CardRegistry.asset` + `Assets/Scripts/Network/CardRegistry.cs`의 `allCards` 배열이 양방향 딕셔너리 열거를 지원하는 단일 원천. 카드 목록을 새로 만들지 말고 이 창구를 통한다.
- **카드 식별자**: `CardData`에 정수 id/guid 없음. 코드는 에셋 `ScriptableObject.name`(한글 파일명)을 사실상 키로 사용(`DeckSaveManager`가 그럼). 소유 저장도 같은 규약을 따른다 — 단 이 취약점은 지뢰 참조.
- **그리드 셀**: `Assets/Scripts/UI/CardElement.cs`를 도감 셀로 재활용. `Init(CardData, CardElementMod.Simple)`로 초상 표시, `SetButtonAction`으로 상세 탭 연결, `SetInteractable(_, disabledOverlay)`로 미보유 잠김 표현. 드래그 훅은 미배선(도감 불필요).
- **그리드 생성 패턴**: `DeckBuilderUI.InitializeSlots`(Content Transform에 셀 Instantiate, 갱신 시 자식 Destroy 후 재생성)를 복제. 프로젝트엔 스크롤/그리드를 코드로 만드는 선례가 없다 — **ScrollRect·GridLayoutGroup(3열)·ContentSizeFitter·고정 Header는 프리팹에서 구성**하고 코드는 셀만 채운다.
- **UI 등록/오픈**: `PooledUIBase` 상속 + Addressables **"UIPrefab" 라벨** 등록 → `DataLibrary` 자동 프리로드. 오픈은 `UIPoolManager.AddOrUpdateUI<T>(data)`, 데이터는 `UIData` 파생으로 주입(`KeywordExplainData`/`SimpleYNPopupData` 관례).
- **카드 상세 팝업**: `PooledCardElement` + `KeywordExplainPopupUI` 흐름 재활용 후보. 스크롤/탭 구분엔 `LongPressDetector`.
- **세이브 배관**: `Assets/Scripts/Battle/DeckSaveManager.cs`의 `Application.persistentDataPath` + `JsonUtility` 패턴을 참조 구현으로. 확인 팝업은 `SimpleYNPopup`.
- **부팅 훅**: `MainMenuInitializer.Awake`(`[DefaultExecutionOrder(-100)]`)가 유일한 초기화 진입점. 세이브 로드·오프라인 정산 부팅을 여기 인접에 건다(중앙 부트스트랩은 없음).
- **진입점**: `MainMenuManager`의 패널 토글 방식에 도감 진입 버튼/패널 추가.

## 신규로 필요한 것 (레이어 배치 방침 — 구현은 담당 에이전트)

- **도감 전용 재화 보관·수확 서비스**: 잔액 획득/차감/변경 이벤트. "도감 전용 최소"로 시작하되, 상위 기획이 단일 골드 범용화를 예정하므로 그 방향을 막지 않는 경계로 둔다(지뢰 참조).
- **도감 세이브 모델**: 소유 카드 집합, 각 행 생산 anchor(마지막 수확/생산 기준 시각), 미수확 누적량, 완성보상 수령 플래그. 카드 추가 시에도 기존 데이터가 유지되는 스키마여야 함(확장성 요구).
- **행 생산 규칙**: 행 완성 판정, 쿨타임·상한, 오프라인 경과시간 → 누적량 산정, 수확 처리.
- **카드 소유/해금 모델 + 디버그 해금 도구**: 보유 여부 저장·판정, 개발자용 해금 트리거.
- **도감 UI 컨트롤러 + 프리팹**: 세로 스크롤 갤러리, 행별 생산 상태 위젯, 진행도(`n/전체`), 완성보상 버튼.
- **카드 상세 팝업**: 확대 + 정보(틸트 없음).

## ⚠️ 가장 틀리기 쉬운 지점 (판단 재료 — 해법은 담당 에이전트)

- **오프라인 생산 anchor 갱신**: 경과시간을 누적으로 환산할 때 기준 시각 갱신 타이밍을 틀리면 재화가 증발하거나 무한 증식한다. 수확·상한도달·부분수확 각각에서 anchor가 어떻게 이동하는지가 핵심.
- **세이브 확장성 vs 카드명 키 취약점**: 소유·행 진행도를 카드 `name`(한글 파일명)에 묶으면 카드 추가엔 견디지만 **파일명 변경 시 세이브가 깨진다**(기존 `DeckSaveManager`가 물려준 취약점). 행 인덱스 기반 저장은 카드 순서 변동에 취약. 무엇을 키로 삼을지가 확장성 요구의 성패를 가른다.
- **행의 동적 재구성**: 카드 수가 3의 배수가 아닐 때 마지막 행, 카드 추가로 행이 늘 때 기존 행 생산 상태 보존 — 진행도·완성조건이 이를 자동 반영해야 함.
- **재화 서비스 범용화 접점**: 이번은 "도감 전용"이지만 상위 기획은 단일 골드 공유. 도감이 재화에 강결합되면 나중에 전투보상·카드팩이 같은 지갑을 쓸 때 리팩터링 비용이 커진다 — 소비/생산 인터페이스 경계를 미리 얇게.
- **중앙 부트스트랩 부재**: 세이브 로드·오프라인 정산이 UI가 도감을 열기 전에 끝나야 한다. 초기화 순서를 `MainMenuInitializer` 실행순서에 어떻게 태울지.

## 거시 단계 (담당 에이전트 배정)

1. **설계 수렴** — `outgame-engineer`(세이브·재화·생산·소유 모델) + `architecture-engineer`(재화/세이브 경계가 상위 범용화를 막지 않는지, 협업 안전성) 병렬 소집 → 취합.
2. **데이터·서비스 시공** — 도감 세이브 모델, 재화 토대, 행 생산·오프라인 정산, 소유/디버그 해금. → `outgame-engineer`.
3. **UI 시공** — 도감 프리팹(스크롤·3열·행 생산 위젯·헤더·완성보상) + 컨트롤러, 카드 상세 팝업, MainMenu 진입점. → `outgame-engineer` + UI 작업.
4. **검수 게이트** — `tcg-reviewer`(단일진실원·세이브 호환성·데드코드) → 메인이 `Unity_GetConsoleLogs`로 컴파일 검증.

다건 구현이 확정되면 `Workflow`로 정찰→설계→시공(worktree 격리)→검수→통합 파이프라인 가능(토큰 큰 단계에서만).

## 검증 방법 (end-to-end)

- **컴파일**: 시공 후 `Unity_GetConsoleLogs`로 에러 0 확인.
- **해금→도감 반영**: 디버그 해금 도구로 카드 획득 → 도감 갤러리에서 잠김 셀이 보유로 바뀌고, 3칸 채운 행의 생산기가 활성되는지.
- **생산·수확·상한**: 시간 경과(또는 디버그 시간 조작)로 행이 생산 중→수확 가능→상한 도달로 전이하고, 수확 시 재화가 증가하며 anchor가 올바로 갱신되는지.
- **오프라인 누적**: 게임 종료 후 재접속 시 경과시간만큼 누적이 반영되고, 증발/무한증식이 없는지.
- **확장성**: `CardRegistry`에 카드를 1장 추가했을 때 갤러리 칸·행·진행도·완성조건이 코드 수정 없이 따라오고, **추가 이전 세이브(수령한 완성보상·행 진행도)가 유지**되는지 — 이번 플랜의 합격 기준.
- **완성 보상**: 전 카드 보유 시 완성보상 버튼 노출·1회 수령 후 비노출.
