# Collection(도감) 시스템 — 거시 계획

> 이 문서는 **목표와 참고 정보**만 담는다. 클래스 구성·API·알고리즘 등 구현 결정은 각 담당 에이전트가 판단한다.

---

## 1. 목표

전투만 있는 게임에 **아웃게임 레이어 첫 조각**을 세운다. 도감은 열람 화면이자 재화 생산 시설이다 — 행을 완성하면 생산기가 켜지고, 쿨타임마다 재화가 쌓이며, 상한 도달 전에 재접속해 수확해야 한다. 이로써 "카드를 모을 이유"와 "재접속할 이유"가 동시에 생긴다.

현재 코드에 재화·시간 개념이 **0건**이므로, 이 작업은 앞으로 붙을 상점·뽑기가 공유할 **재화 서비스와 세이브 규약의 기준점**이 된다.

| 항목 | 값 |
|---|---|
| 화면 | 모바일 세로 9:19 |
| 도감 | 전체 카드 = 도감 1개, **3열 그리드**. **행은 카드 수에 따라 자동 확장** |
| 뷰 형태 | **세로 스크롤 갤러리** — 드래그로 아래로 내려 훑는다 |
| 생산 단위 | **행(row)**. 행 하나가 곧 하나의 생산기 |
| 해금 | **디버그 도구로만** (뽑기·전투보상은 이번 범위 밖) |
| 재화 | **범용 재화 서비스** 신설. 컬렉션은 소비자 중 하나 |
| 감상 | **카드 틸트** |

**효과 3종**
1. **재화 생산** — 행(3칸) 완성 시 생산기 활성. 쿨타임마다 생산, 상한 있음, 오프라인 누적 후 수확
2. **완성 보상** — 도감 전체 완성 시 1회성 보상
3. **상세 열람** — 카드 클릭 → 카드 상세 정보 + 틸트 인터랙션

### 화면 구조 — 세로 스크롤 갤러리, 행 = 생산 유닛

전체 갤러리는 **하나의 세로 스크롤 뷰**다. 유저는 드래그로 아래로 내리며 도감 전체를 훑고, 카드가 늘면 스크롤 길이가 그만큼 길어진다. 화면에 한 번에 다 보이는 고정 레이아웃이 아니다.

스크롤 안에 쌓이는 단위는 **행(row)** 이고, **행 하나가 곧 하나의 생산기**다. 행마다 카드 3칸과 그 행 전용 생산 상태 표시가 함께 붙어 있어, 유저는 "이 줄을 채우면 이 줄에서 자원이 나온다"를 한눈에 본다.

```
 ┌─────────────────────────────┐
 │  ← 뒤로    기본 도감   💰 1,240 │  ← 헤더 (스크롤에 고정)
 ├─────────────────────────────┤
 │  진행도  ███████░░░  7 / 9    │
 ├─────────────────────────────┤ ┐
 │ ┌───┐ ┌───┐ ┌───┐  ┌──────┐ │ │
 │ │카드│ │카드│ │카드│  │💰 24 │ │ │  행 = 카드 3칸 + 그 행의 생산기
 │ └───┘ └───┘ └───┘  │ 수확 │ │ │  (완성 → 생산 중, 수확 가능)
 │                     └──────┘ │ │
 │ ┌───┐ ┌───┐ ┌───┐  ┌──────┐ │ │
 │ │카드│ │ ? │ │카드│  │  🔒  │ │ │  (미완성 → 잠김)
 │ └───┘ └───┘ └───┘  └──────┘ │ │  세로로 드래그해
 │ ┌───┐ ┌───┐ ┌───┐  ┌──────┐ │ │  계속 내려간다
 │ │카드│ │카드│ │카드│  │ 만땅 │ │ │  (상한 도달 → 수확 재촉)
 │ └───┘ └───┘ └───┘  └──────┘ │ │
 │            ⋮                 │ │  카드가 늘면 행이 계속 추가됨
 ├─────────────────────────────┤ ┘
 │   [ 도감 완성 보상 받기 ]      │  전부 보유 && 미수령일 때만
 └─────────────────────────────┘
```

행이 가질 수 있는 상태: **잠김**(미완성) / **생산 중** / **수확 가능** / **상한 도달**. 행마다 독립적이며, 서로의 진행도에 영향을 주지 않는다.

### ★ 확장성 요구 — 도감은 고정 크기가 아니다

**카드가 추가되면 도감이 자동으로 늘어나야 한다.** 3행은 현재 카드가 9장이라 나온 결과일 뿐 설계 상수가 아니다. 카드를 새로 만들었을 때 개발자가 손대야 하는 것은 최소여야 하고, 다음이 자동으로 따라와야 한다:

- 갤러리에 새 칸이 생기고, 3열을 채우면 **새 행이 생성**된다
- 새 행에도 **생산기가 붙는다**
- **도감 완성 조건과 진행도 표시**(`n / 전체`)가 새 카드를 포함하도록 갱신된다
- **기존 유저의 세이브가 깨지지 않는다** — 이미 수령한 완성 보상, 진행 중이던 각 행의 생산 진행도가 그대로 유지돼야 한다

> 이 요구 때문에 **행의 식별 방식**과 **도감에 실릴 카드 목록을 어디서 얻을지**가 이 기능의 핵심 갈림길이 된다. 행을 "몇 번째 줄"로 식별하면 카드가 하나만 끼어들어도 이후 모든 행의 진행도가 밀린다. 또 카드 마스터 목록이 이미 `CardRegistry.asset` / `DeckBuilderUI.cs:10` / `MainMenuInitializer.cs:8` **세 곳에 중복**되어 있고 순서도 서로 달라서, 도감이 네 번째 목록이 되면 "카드는 추가됐는데 도감에만 안 나오는" 드리프트가 생긴다. 해법은 담당 에이전트가 정하되 이 두 지점은 반드시 의식할 것.

## 3. 참고 — 기존 코드베이스 / 인프라

### CardData — `Assets/Scripts/Card/CardData.cs`
도감에서 쓸 필드: `displayName` / `cardExplain` / `maxHp` / `bonusHp` / `keywords` / `explainKeywords` / `SynergyData[] synergies`(중복은 소비측에서 `Distinct`) / 일러스트 4종(`fullImage`·`portrait`·`battleImage`·`deckPreview`) / 보이스 5종(`spawnVoices`·`attackVoices`·`killVoices`·`deathVoices`·`effectVoices`).

- 카드 9장: `Assets/SO/Cards/` (아트록스·피즈·그웬·킨드레드·마오카이·오른·뽀삐·람머스·티모)
- **등급/랭크/코스트 필드는 없음** (단일 도감 프로토타입이라 무관)
- `weaponPrefab`은 전투 연출용 무기 모델이며 **도감에서는 쓰지 않는다**
- ⚠️ `CardElement.cs:48`은 카드 이름을 `_card.name`(에셋 파일명)으로 표시한다. 도감에서는 **`displayName`이 정본**

### SynergyData — `Assets/Scripts/Card/SynergyData.cs`
`displayName` / `effectDescription` / `Color color` / `Sprite icon` / `SynergyTier[] tiers` 보유 → 상세 화면 시너지 배지에 그대로 쓸 수 있다. 에셋 7종 `Assets/SO/Synergies/`.

### UI 인프라 — `Assets/Scripts/UI/UIManager/`
- `UIPoolManager.AddOrUpdateUI<T>(UIData)` / `HideUI<T>()` / `ShowUI<T>()` — `PooledUIBase` 상속 UI를 띄우는 진입점
- `UIAnimator` — DOTween 래퍼 (`Fade` / `FadeGraphic` / `Move`)
- `DataLibrary` — Addressables 라벨 **`"UIPrefab"`** 로 `PooledUIBase` 프리팹을 선로드

**신규 팝업 추가 절차**: `PooledUIBase` 상속(`Initialization`/`Show`/`Hide` 구현, `contents` 연결) → `UIData` 파생 클래스를 같은 `.cs` 하단에 정의(기존 관례) → 프리팹을 `Assets/Assets/Prefabs/UI/PooledUI/`에 배치 → **Addressable 체크 + `UIPrefab` 라벨 부여**(누락 시 런타임 에러만 나고 컴파일로 안 잡힘).

### 세로 스크롤 갤러리 참고 사례 — `DeckBuilderUI` (MainMenu 씬)
덱 편집 화면에 이미 같은 형태의 스크롤 갤러리가 있다. **구조만 참고**하고 코드는 새로 쓴다.
- `ScrollRect` — `m_Horizontal: 0` / `m_Vertical: 1` (**세로 전용**), Elastic
- Content에 `GridLayoutGroup` — `cellSize 500×900`(세로로 긴 카드 비율), `spacing 100`, Flexible 제약 → 레퍼런스 폭 1440에서 자연히 2열이 됨. **도감은 3열이므로 셀 크기·간격을 다시 잡아야 한다**
- 셀 생성은 `InitializeSlots()`에서 자식을 **전량 `Destroy` → 전량 `Instantiate`** (풀링·가상화 없음). 카드 9장에선 무해하지만 도감이 커지는 것을 전제하면 그대로 답습할지 판단할 것

> 도감은 "그리드 하나에 셀을 쭉 붓는" 이 구조와 다르다. **행이 생산 단위이므로 행이 실체를 가져야 한다** — 셀을 평평하게 나열하고 3개씩 끊어 읽는 방식으로는 행 상태(잠김/생산/수확/만땅)를 표현하기 어렵다.

### 세이브 참고 사례 — `Assets/Scripts/Battle/DeckSaveManager.cs`
`static` 클래스 + `Application.persistentDataPath` + `JsonUtility`, **카드를 에셋 `name` 문자열로 저장**(배열 인덱스 아님). 도감 세이브는 이 파일을 재사용하지 않되, 문자열 식별 방식은 참고할 만하다 — 인덱스 식별은 `CardRegistry` 순서 불변식에 묶이기 때문이다.

### 따를 만한 관용구
`GameTiming.cs` / `SynergyResolver.cs` / `SynergyApplier.cs`가 **"순수 static 파사드 + SO 설정"** 패턴을 확립해 두었다. 씬 배선 없이 동작하고 `DontDestroyOnLoad` 싱글턴을 늘리지 않는다.

### 화면 설정 현황
`MainMenu.unity` / `CollectionTest.unity` 캔버스는 **1440×3120(≈9:19.5)**, `Scale With Screen Size` + **폭 기준 매칭**. 세로 게임에 맞는 설정이므로 도감도 여기 맞춘다. (`BattleScene`만 1080×1920이며 도감과 무관)

`CollectionTest.unity`는 현재 `MainMenu.unity`의 **바이트 단위 완전 복사본**(diff 0줄)이라 도감 전용 요소가 아직 없다. 작업 샌드박스로 쓴다.

## 4. 구현 계획 (거시)

### 0단계 · 정리
스크립트 폴더에 섞여 있는 7MB 목업 PNG를 이미지 폴더로 이동.

### 1단계 · 토대 — 데이터·로직 레이어 (UI 없음)
시각 창구, 재화 서비스, 생산 계산, 도감 정의와 그 에셋, 소유·수확 상태, 영속화.

> **도감 정의와 재화 타입은 2·3단계가 모두 읽는 공유 계약이다. 이 둘을 먼저 확정·동결한 뒤 나머지를 시작한다.**
> 특히 **도감이 카드 추가에 따라 자라는 방식**과 **행 식별자**를 여기서 결정한다(§1 확장성 요구 참조). 이 둘을 나중에 바꾸면 세이브 마이그레이션이 필요해진다.

### 2단계 · 갤러리 화면
갤러리 셀 → **행(셀 3개 + 그 행의 생산기)** → 세로 스크롤 루트 → 재화 헤더 → 프리팹 배치.

> **행 수를 화면에 하드코딩하지 않는다.** 행은 데이터 기준으로 세로 스크롤 안에 생성·증감되어야 하며, 카드가 늘어도 씬·프리팹을 다시 손대지 않아야 한다.
> **행 프리팹이 이 화면의 핵심 단위**다. 카드 칸과 생산기 표시가 한 프리팹 안에 있어야 "행 = 생산기"라는 구조가 UI에서도 유지된다. 행은 잠김/생산 중/수확 가능/상한 도달 네 상태를 스스로 표현한다.
> 갤러리 셀은 `PooledUIBase`로 만들 수 없다 — `UIPoolManager`가 `Dictionary<Type, …>` 기반이라 **타입당 인스턴스 1개**뿐이다. 셀처럼 N개 동시 표시가 필요한 것은 직접 `Instantiate` 하거나 `ObjectPooler`를 쓴다.

### 3단계 · 상세 팝업 + 디버그 도구
상세 팝업 → 틸트·홀로 연출 → 프리팹 + `UIPrefab` 라벨 → 디버그 패널(해금 토글·재화 지급·**시간 점프**).

> 카드를 기울여도 입체감이 나오려면 **원근이 필요하다.** Canvas가 `Screen Space - Overlay`면 X/Y 회전이 평면 축소로만 보인다. 착수 시 현재 캔버스 렌더 모드부터 확인할 것.
> 디버그 패널의 **시간 점프**는 오프라인 생산·상한·수확을 앱 재시작 없이 검증하는 유일한 수단이므로 1단계 시각 설계 때부터 고려한다.

### 4단계 · 통합
`MainMenuManager`에 진입 경로 추가 → 세이브 로드 부트(`MainMenuInitializer`의 `[DefaultExecutionOrder(-100)]` 패턴 참고) → 검증된 프리팹을 `MainMenu.unity`로 이동.

> ⚠️ `MainMenuManager`에는 패널 스택이 없다. `OnBackPressed`(`:84-94`)가 모든 패널을 끄는 브루트포스 방식이므로, **도감 패널을 여기에도 반영하지 않으면 뒤로가기 버그**가 난다.

### 병렬 작업 시 유일한 실질 충돌원 = 씬/프리팹 (Unity는 머지 불가)
- 2단계와 3단계는 **서로 다른 프리팹**을 만들도록 분리한다
- `MainMenuManager.cs` / `MainMenuInitializer.cs` 수정과 씬 배치는 **4단계에서 한 사람이 몰아서** 처리한다
- 작업은 **`CollectionTest.unity`** 에서 한다. `MainMenu.unity`는 4단계에서만 건드린다
