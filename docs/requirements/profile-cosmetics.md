# 꾸미기 아이템(CosmeticItem) 소유·지급 확장

2026-09-22. 사용자 리뷰 반영: 칭호 제외, 기존 아이템 기본 소유, 미소유 아이템 숨김, 지급 후 목록 추가. CosmeticItem 시트 신설 승인에 따라 docs/SpecData/CosmeticItem_sheet.csv에 기존 31개 항목을 등록했다. 소유·지급·뷰 및 로컬 검증을 구현했다. Firestore 표 업로드와 원격 배포는 미수행이며 검증 범위는 아래 기록을 따른다.

## Overview

아바타·프레임·이모티콘을 계정이 영구 소유하고 장착하는 외형 아이템으로 관리한다. 기존 아이템은 기존 계정과 신규 계정 모두 기본 소유한다. 이후 추가되는 획득형 아이템은 보상·상점 등에서 지급받아야 프로필 선택 목록에 나타난다.

아이템 전송은 서버가 해당 계정에 지급하는 것을 뜻한다. 유저 간 거래·선물은 포함하지 않는다.

## Goals

- 아바타·프레임·이모티콘의 소유 상태와 장착 상태를 저장하고 재접속 시 복원한다.
- 기존 아이템을 기본 소유로 보장하면서 향후 아이템을 지급형으로 추가할 수 있게 한다.
- 소유한 아이템만 프로필 선택 목록에 표시하고 지급 직후 목록을 갱신한다.
- 보상·상점이 기존 서버 공통 지급 경로를 통해 아이템을 지급하도록 확장한다.
- 재시도와 동시 요청에도 소유 유실·중복 차감이 발생하지 않게 한다.

## Out of Scope

- 칭호의 데이터·세이브·지급·선택 UI 변경. 기존 칭호 동작은 유지한다.
- 유저 간 거래·선물, 우편함, 기간제 소유권, 소모·분해·판매.
- 신규 아트 제작, 실제 상점 상품·가격 저작, 상점 화면 신설.
- 미소유 아이템의 프로필 미리보기·잠금 칸·해금 조건 표시.
- 운영 서버·Firestore 규칙·Addressables 배포.
- SpecData.bytes 재생성 및 자동 생성 C# 파일 수동 수정.

### 기본 소유

현재 저작된 다음 항목을 기존·신규 계정 공통 기본 소유 대상으로 고정한다.

| 종류 | 개수 | ID |
|---|---|---|
| 아바타 | 3 | avatar_00, avatar_01, avatar_02 |
| 프레임 | 7 | frame_default, frame_Sun, frame_Emerald, frame_Frost, frame_Rose, frame_Moon, frame_Ocean |
| 이모티콘 | 21 | 1부터 21까지 |

2026-09-22 Assets/SO/Profile/ProfileConfig.asset 및 Assets/SO/EmoteCatalog.asset에서 확인했다. 구현 착수 시 다른 작업으로 목록이 바뀌었는지 대조한다.

- 카탈로그 전체를 매번 기본 소유로 처리하지 않는다. 신규 항목을 추가하는 것만으로 기존·신규 계정에 자동 해금되지 않아야 한다.
- 기본 소유 목록은 명시적인 저작값으로 관리하며, 추가 항목의 기본 지급 여부는 기본적으로 꺼져 있어야 한다.
- 구 계정의 소유 필드가 없으면 서버가 기본 소유를 보완한다. 기존 획득 목록과 장착값을 덮어쓰지 않는다.
- 초기화·보완 처리를 반복해도 소유가 늘거나 줄어들지 않는다. 계정의 정당한 추가 획득은 유지한다.

### 소유·장착·저장

- ProfileSaveData에 세 종류의 소유 목록을 추가하고 서버에서 확정한 값을 채택한다. 필드 후보는 ownedAvatarIds·ownedFrameIds·ownedEmoteIds다.
- 기존 ID 계약을 유지한다. 아바타·프레임은 문자열, 이모티콘은 양의 정수이며 0은 빈 장착 칸이다.
- 소유는 영구 해금이다. 같은 아이템을 다시 받아도 수량·중복 셀이 늘지 않는다.
- 소유 목록 변경은 서버가 담당한다. 클라이언트가 임의로 목록을 추가·삭제하지 못하도록 Firestore 규칙과 세이브 업로드 경로를 함께 맞춘다.
- 장착 요청은 해당 종류의 유효한 ID이며 소유한 항목인지 검증한다. 뷰에서 숨기는 것만으로 장착 제한을 대신하지 않는다.
- 아바타·프레임은 기본 항목을 보장한다. 이모티콘은 기존 6칸·순서·빈 칸·중복 장착 금지 규칙을 유지한다.
- 서버 응답 채택으로 소유가 갱신되면 ProfileManager와 뷰에 알린다. 이 과정에서 불필요한 Save를 발화하지 않는다.
- 서버 확정 소유와 편집 중인 장착 후보를 분리한다. 지급 응답이 닉네임·장착 후보를 되돌리거나 칭호 상태를 변경하지 않는다.
- 클라이언트가 아직 표시할 수 없는 지급 ID는 소유 기록에서 삭제하지 않는다. 표·아트 배포 불일치를 드러내고 표시 가능한 시점에 노출한다.

### 프로필 뷰

- 아바타·프레임·이모티콘 선택 목록에는 소유하고 표시 데이터가 있는 항목만 셀을 만든다.
- 미소유 항목의 잠금 그림·실루엣·빈 자리·미리보기는 표시하지 않는다. 기존 초안의 자물쇠·흑백 미소유 표현은 폐기한다.
- 지급 성공 응답을 채택하면 열린 목록에도 새 항목을 추가한다. 뷰가 닫혀 있으면 다음 열기에 반영한다.
- 추가 항목은 카탈로그 저작 순서를 따른다. 기존 장착값·편집 후보·열린 탭·가능한 범위의 스크롤 위치를 유지한다.
- 지급 자체는 자동 장착하지 않는다. 사용자가 새 항목을 선택하고 기존 확정 흐름으로 장착한다.
- 이모티콘의 고정 장착 6칸은 유지한다. 미소유 목록 항목을 숨기는 규칙과 빈 장착 칸을 혼동하지 않는다.
- 칭호 탭은 이 필터·갱신 변경의 대상이 아니다.

### 공통 서버 지급

- 기존 rewardTable 및 grantRewardItems를 확장한다. 종류는 Avatar·Frame·Emote, 식별자는 기존 카탈로그 ID를 사용한다.
- 지급 수량은 영구 해금 의미에 맞게 1로 제한한다. 중복 지급은 소유를 유지하고 중복 결과를 반환하며 별도 보상 재화를 임의로 만들지 않는다.
- 클라이언트는 보상·상품 식별자를 전달한다. 실제 아이템·가격·수령 자격은 서버가 검증한다.
- 소유 변경·재화 차감·수령 기록을 같은 트랜잭션으로 확정한다. 실패 시 일부만 반영하지 않는다.
- 요청 식별자와 수령 기록으로 재요청을 구분한다. 단순 소유 중복 검사와 결제 중복 방지는 별도로 처리한다.
- 이미 소유한 단품의 새 구매는 차감 전에 거절한다. 이미 성공한 동일 구매의 재요청은 기존 성공 결과를 반환한다.
- 기존 보상 진입점의 응답·클라이언트 파싱·획득 표시에도 새 종류를 전달한다. 미래 상점은 같은 지급 로직을 재사용할 수 있어야 한다.
- 일반 사용자가 임의의 아이템 ID만 보내 지급받는 무조건 지급 API는 두지 않는다.

### 카탈로그 및 배포 경계

- 서버 지급 검증용 정식 카탈로그는 시트 기반으로 관리하고 기존 SO는 Sprite·AnimationClip 등 표시 자산을 담당한다.
- 승인된 표는 CosmeticItem이며 열은 id(int), itemType(string), itemId(string), defaultOwned(int)다. 저장소 진실원은 docs/SpecData/CosmeticItem_sheet.csv다. itemType+itemId는 고유해야 하고 Emote의 itemId는 양의 정수 ID로 검증한다. 기존 세이브 ID를 새 행 번호로 치환하지 않는다.
- defaultOwned는 0 또는 1만 사용한다. 기존 31개 항목은 1이며 향후 획득형 항목은 0으로 추가한다. 새 행의 id는 기존 번호를 재사용하지 않고 추가한다.
- 사용자 지시로 로컬 CSV 시트를 신설했다. 후속 배포 지시로 Firestore 반영을 완료했다. 원격 Google Sheets 및 생성 C#·SpecData.bytes는 갱신하지 않았다.
- 필수 표 등록으로 기존 앱 초기화를 깨뜨리지 않도록 서버·클라이언트·표 반영 순서와 구 계정 호환성을 구현 전에 확인한다.

### 상용 사례에서 적용할 원칙

- VALORANT는 플레이어 카드·칭호 등의 획득 경로로 보상과 상점을 사용하고 액세서리 상점에서 보유 항목을 제외한다. 이 프로젝트도 획득 경로와 소유 상태를 분리한다. 프로필에서 미소유 항목을 숨기는 UI는 이번 사용자 결정이다. [Riot 공식 설명](https://playvalorant.com/en-us/news/game-updates/progression-update-explainer-faq/)
- PlayFab Economy는 IdempotencyId로 같은 거래의 중복 실행을 방지한다. 이 프로젝트도 네트워크 재시도를 새 구매로 처리하지 않아야 한다. 기존 Firebase 트랜잭션·수령 기록 구조를 활용하며 PlayFab 도입을 의미하지 않는다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/xbox/playfab/economy-monetization/economy-v2/tutorials/idempotent-transactions-and-retries)

## 구현·검증 기록 (2026-09-22)

- `CosmeticItem`은 서버 전용 CSV 발행 표다. 업로더 목록·검증·발행 인덱스에 등록했으며 클라이언트 필수 `TableNames`에는 넣지 않았다. 생성 C# 및 `SpecData.bytes`는 변경하지 않았다.
- 신규 계정 기본 소유와 구 계정 `ensureProfileCosmetics({env})` 보완을 구현했다. 구 계정은 소유 필드 누락 시 보완 후 문서를 재조회한다. 표가 미발행이면 명시 오류이며 임시 기본 소유 폴백은 없다.
- 서버 소유 필드와 클라이언트 편집 필드를 분리했다. 일반 지급 응답은 편집 중 값을 보존하고 `devResetSave`만 외형 장착을 초기화한다. 소유 채택은 Save를 호출하지 않는다.
- 공통 지급·보상 응답·경험치 병합·프로필 증분 갱신·아이콘 기반 결과 표시를 연결했다. 실제 상점 상품이나 임의 지급 callable은 추가하지 않았다.
