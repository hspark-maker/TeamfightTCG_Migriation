# 글로벌 업적

진행도의 진실원은 `envs/{env}/users/{uid}/statistics/current`의 플레이어 누적 통계다. 업적은 이 통계를 읽어 조건을 판단하고, 단계별 수령 기록은 `achievements/current`에 보관한다. 같은 문서의 진행도 필드는 구버전 호환을 위한 통계 사본으로 유지하며 새 집계는 통계 시스템에서만 한다. 전환·이관 방식은 [플레이어 통계](PlayerStatistics.md)를 따른다.

일일·주간 초기화는 없으며 클라이언트 쓰기는 허용하지 않는다. 이전 단계 보상을 받지 않아도 다음 단계 진행도는 계속 쌓이고, 각 단계 보상은 한 번만 받을 수 있다.

## 집계 기준

| 종류 | 기준 | 초기 목표 |
| --- | --- | --- |
| 승리 | 서버에서 검증한 정상 완료 전투 승리 | 1 / 10 / 30 / 100 / 300 |
| 카드 파괴 | 서버 전투 기록의 상대 카드 파괴 수 | 10 / 50 / 200 / 1,000 / 3,000 |
| 시너지 플레이 | 시작 덱에서 해당 시너지가 활성화된 정상 완료 전투; 승패 무관 | 각각 1 / 10 / 30 / 100 / 300 |
| 앨범 완성 | 잠기지 않은 테마의 모든 카드를 소유; 완성 보상 수령 여부 무관 | 1 |
| 연승 | 정상 완료 전투의 최고 연승; 패배·무승부는 현재 연승 초기화 | 2 / 3 / 5 / 7 / 10 |
| 팩 개봉 | 서버에서 성공한 구매 팩과 보상 팩 개봉; 직접 카드 지급 제외 | 1 / 10 / 30 / 100 / 300 |

시너지 트랙은 `SynergyDef`의 Brand(낙인), Bulk(덩치), Caretaker(돌보미), Flow(흐름), Legacy(유산), Predator(포식자), Scale(비늘), Trace(추적) 8개다. 튜토리얼·테스트 전투와 미완료·검증 실패 결과는 집계하지 않는다. 앨범은 기존 소유 상태를 역산하고, 승리·파괴·시너지 플레이·연승·팩 개봉은 기능 도입 후부터 기록한다.

현재 해금된 앨범 테마는 `Theme_Nature` 하나이므로 달성할 수 없는 2개 이상의 목표는 넣지 않았다. 새 테마를 해금할 때 해당 그룹에 다음 단계를 추가한다.

## 데이터와 보상

진실원은 [Achievement_sheet.csv](SpecData/Achievement_sheet.csv)다. 총 13그룹·61단계를 제공한다. 단계 1~5의 초기 보상은 골드 100 / 샤드 20 / 보석 5 / 골드 500 / 보석 20이다. 보석의 내부 재화 키는 `Diamond`다. 초기 수치는 밸런스 조정용이며 각 행에서 독립적으로 변경할 수 있다.

`achievementId`는 수령 낙인 키이므로 출시 후 재사용하거나 이름을 바꾸지 않는다. `groupId`와 `stage`는 단계 순서를, `eventKey`와 `synergyId`는 누적 진행도 종류를 정한다. 프로필 프레임·아이콘·칭호·카드 스킨 지급은 포함하지 않는다.

## 발행과 확인

`Achievement`는 서버 전용 표다. `SpecFirestoreUploader`가 전용 DTO로 CSV를 읽고, 표 선택 목록과 콘텐츠 인덱스 발행에 포함한다. 클라이언트는 `getAchievements` 응답으로 정의를 받는다. 생성 테이블이나 `SpecData.bytes`에 업적을 추가하지 않는다.

로컬 구현만으로 기존 배포 서버에 기능이 생기지는 않는다. 적용 시 업적 callables와 전투·팩 집계 서버 코드, Firestore 규칙, `Achievement` 표 및 콘텐츠 인덱스, 클라이언트 UI 반영이 필요하다. 초기 구현 단계에서는 원격 업로드·배포 및 `SpecData.bytes` 재생성을 수행하지 않았다. 이후 서버 배포 상태는 아래 기록을 따른다.

업적 도입 전 릴리스에는 이 표가 없으므로 롤백 검증은 기존 릴리스의 업적 표 누락을 허용한다. 새 릴리스를 발행할 때에는 다른 서버 표처럼 업적 표 업로드와 해시 일치를 확인한다. 제한된 보상 표 갱신용 `publish-local-spec.js`도 업적 CSV를 읽을 수 있지만, 신규 표의 최초 발행은 에디터의 정식 발행 경로를 사용한다.

오프라인 확인에는 CSV 스키마·고유 키·단계 순서·목표 증가·시너지 참조·달성 가능한 앨범 목표 검증과 서버 카탈로그 검증을 사용한다. `SpecSheetsUploadValidation`은 실제 업적 CSV를 전용 발행 파서에 넣고 보상 열 누락을 거절하는지도 확인한다. 실제 기기 화면과 배포 환경의 통합 동작은 별도 확인 대상이다.

2026-09-21 로컬 검증: 신규 업적 테스트 20개와 관련 회귀를 합친 서버 테스트 38개 통과. Firestore 에뮬레이터에서 중복·동시 수령, 영수증 만료 후 재청구, 트랜잭션 실패 시 취소, 구매·보상 팩 및 전투 정산 집계를 확인했다. TypeScript·Unity 런타임·에디터 코드 컴파일과 변경 서버 코드 린트가 통과했다. 클라이언트 실제 관리자 코드를 별도 실행한 15개 검사에서 단계 수령, 누적 진행, 오래된 응답 거부, 계정 초기화를 확인했고 신규 프리팹의 내부 참조도 검사했다. 실제 Unity 화면 플레이 검증은 수행하지 않았다.

2026-09-21 데이터 검증: 실제 C# 발행 파서와 CSV 파서로 310항목·61행을 확인했다. Node 발행 파서의 재화·스키마 오류 거절, 실제 시너지 8종 참조, 현재 앨범 목표 도달 가능 여부도 통과했다. 이 검증은 읽기 전용이며 시트·Firestore·생성 산출물을 변경하지 않았다.

## 서버 배포 완료 (2026-09-21)

사용자 지시에 따라 `bm-cardbattle` / `asia-northeast3`에 함수 11개를 배포했다: `getAchievements`, `claimAchievement`, `submitMatchResult`, `openPack`, `claimAttendance`, `claimMission`, `claimReward`, `claimPassReward`, `claimBattleExperience`, `spinRoulette`, `getOnboardingOperation`. `cardbattle` 데이터베이스의 Firestore 규칙도 배포했다. 이미 배포된 룰렛 순환 추첨 코드와 일치하는 소스를 사용했다.

배포 전 전체 린트·TypeScript 빌드·테이블 세대 일치 검사·규칙 컴파일 통과. 배포 후 11개 함수의 ACTIVE 상태와 신규 callable 2개의 인증 없는 요청 거절(401/UNAUTHENTICATED)을 확인했다. 작업 증거는 `Build/AchievementDeployment-20260921-164900/verification.json`에 있다.

조회 시점에 test/live 모두 `Achievement` 표와 인덱스 항목은 아직 없었다. 업적 적용용 업로드 대상은 `Achievement` 1개(61행)이며 별도 `Reward` 변경은 없다. Unity의 `Tools > Card Battle > 릴리즈 관리 > 데이터`에서 대상 환경과 `Achievement`를 선택하고, **업로드 후 공개 시리얼 올리기**를 켜서 **업로드 + 공개**한다. 업적만을 위해 테이블 세대를 올리거나 `SpecData.bytes`를 생성할 필요는 없다. 다른 미발행 표의 해시 차이로 공개가 거절되면 해당 표의 별도 변경을 확인한다.

이번 서버 배포에는 테이블 업로드·Hosting 리소스 배포·APK 빌드는 포함하지 않았다. 새 C# UI를 실행하려면 새 클라이언트 빌드가 필요하다. 실제 계정의 수령 및 기기 화면 검증은 테이블 발행과 클라이언트 반영 뒤에 수행한다.
