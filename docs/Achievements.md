# 글로벌 업적

진행도의 진실원은 `envs/{env}/users/{uid}/statistics/current`의 플레이어 누적 통계다. 업적은 이 통계를 읽어 조건을 판단하고, 단계별 수령 기록은 `achievements/current`에 보관한다. 같은 문서의 진행도 필드는 구버전 호환을 위한 통계 사본으로 유지하며 새 집계는 통계 시스템에서만 한다. 전환·이관 방식은 [플레이어 통계](PlayerStatistics.md)를 따른다.

일일·주간 초기화는 없으며 클라이언트 쓰기는 허용하지 않는다. 이전 단계 보상을 받지 않아도 다음 단계 진행도는 계속 쌓이고, 각 단계 보상은 한 번만 받을 수 있다.

## 집계 기준

| 종류 | 기준 | 초기 목표 |
| --- | --- | --- |
| 승리 | 서버에서 검증한 정상 완료 전투 승리 | 1 / 10 / 30 / 100 / 300 |
| 카드 파괴 | 서버 전투 기록의 상대 카드 파괴 수 | 10 / 50 / 200 / 1,000 / 3,000 |
| 시너지 플레이 | 시작 덱에서 해당 시너지가 활성화된 정상 완료 전투; 승패 무관 | 각각 1 / 10 / 30 / 100 / 300 |
| 앨범 완성 | 잠기지 않은 테마의 모든 카드를 소유; 완성 보상 수령 여부 무관 | 1 |
| 연승 | 정상 완료 전투의 최고 연승; 패배·무승부는 현재 연승 초기화 | 2 / 3 / 5 / 7 / 10 |
| 팩 개봉 | 서버에서 성공한 구매 팩과 보상 팩 개봉; 직접 카드 지급 제외 | 1 / 10 / 30 / 100 / 300 |

시너지 트랙은 `SynergyDef`의 Brand(낙인), Bulk(덩치), Caretaker(돌보미), Flow(흐름), Legacy(유산), Predator(포식자), Scale(비늘), Trace(추적) 8개다. 튜토리얼·테스트 전투와 미완료·검증 실패 결과는 집계하지 않는다. 앨범은 기존 소유 상태를 역산하고, 승리·파괴·시너지 플레이·연승·팩 개봉은 기능 도입 후부터 기록한다.

현재 해금된 앨범 테마는 `Theme_Nature` 하나이므로 달성할 수 없는 2개 이상의 목표는 넣지 않았다. 새 테마를 해금할 때 해당 그룹에 다음 단계를 추가한다.

## 데이터와 보상

업적 조건의 진실원은 [Achievement_sheet.csv](SpecData/Achievement_sheet.csv), 지급물의 진실원은 [Reward_sheet.csv](SpecData/Reward_sheet.csv)다. 총 13그룹·61단계를 제공한다. Reward의 `ownerType=Achievement`, `ownerId=achievementId`로 단계별 보상을 연결한다. 단계 1~5의 초기 보상은 골드 100 / 샤드 20 / 보석 5 / 골드 500 / 보석 20이다. 보석의 내부 재화 키는 `Diamond`다. 보상 종류·수량은 Reward 행에서 변경하며 Achievement에는 재화·수량을 중복 저작하지 않는다.

`achievementId`는 수령 낙인 키이므로 출시 후 재사용하거나 이름을 바꾸지 않는다. `groupId`와 `stage`는 단계 순서를, `eventKey`와 `synergyId`는 누적 진행도 종류를 정한다. 프로필 프레임·아이콘·카드 스킨 지급은 포함하지 않는다.

칭호도 해당 업적의 Reward 행으로 저작한다. `rewardType=Title`, `rewardId=titleId`, `amount=1`이며 재화는 order 1, 칭호는 order 2다. [Title_sheet.csv](SpecData/Title_sheet.csv)는 `id`·`titleId`만 가진 칭호 ID 목록이다. 조건의 중복 저작이나 실행 시 조건 일치 조인은 하지 않는다. 서버가 `getAchievements.definitions[].reward.items`에 보상 항목을 제공하며, 해당 단계 수령 시 재화·칭호 소유·영구 수령 마커를 원자적으로 저장한다. 집계 달성이나 접속만으로 지급하지 않는다. 현재 연결은 `win.1/2/4/5`, `destroy.2`, `album.1`, `streak.1`, `pack.2`의 8종이다. 이미 가진 칭호는 유지하며 자동 장착하지 않는다.

2026-09-22 후속 로컬 변경: Achievement의 재화·수량 2열과 Title의 조건·설명 4열을 제거하고 Reward에 업적 재화 61행·칭호 8행을 추가했다. 기존 Reward 213행과 업적·칭호의 안정 키는 보존했다. 새 보상 행 ID는 276~344이며 과거 삭제한 268~275를 재사용하지 않는다. 기존 Title 조건은 최초 이관에서만 업적과 대조했고 이후 연결은 Reward에서 직접 정한다. 이미 수령한 업적의 마커를 초기화하거나 과거 미소유 칭호를 접속 시 소급 지급하지 않는다. 원격 배포·시트 발행·생성 산출물 갱신은 별도다.

개발 빌드·에디터의 F8 → 업적 → **전체 업적 달성 (서버·테스트 전용)**은 `devCompleteAchievements`로 누적 통계를 활성 업적의 최대 목표까지 채운다. 이미 더 높은 값은 유지하고 현재 연승·전투 상세 집계·기존 수령 기록·재화·칭호 소유는 변경하지 않는다. 완료 후 업적 화면에서 순서대로 보상을 수령해 칭호 지급까지 확인할 수 있다. 서버는 인증된 본인의 test 환경만 허용한다. 이 디버그 버튼을 서버에 연결하려면 신규 callable 배포가 필요하다.

2026-09-22 원격 반영 완료: test `6.63 → 6.64`에 Achievement 61행(조건 11열), Title 8행(ID 2열), Reward 282행을 발행했다. 기존 보상 213행·재화 61개·칭호 연결 8개를 검증하고 CAS 단일 커밋 224개 쓰기로 적용했다. 나머지 25표 payload와 이전 불변 릴리스는 보존했다. 전용 발행기는 `functions/scripts/publish-achievement-rewards.js`이며 10개 오프라인 이관 검사도 통과했다. 업적 디버그를 포함한 관련 Functions 16개 배포 후 ACTIVE, 원격 28표 전체 hash·세 표 행 미러·업적 카탈로그 61개·칭호 안내 8개를 확인했다. live 스펙은 `6.11` 그대로이며 Functions 코드는 test/live 공용이다. 실제 플레이어 데이터·규칙·SpecData.bytes·자동 생성 C#은 변경하지 않았다. 실제 계정 달성·수령 플레이는 별도 확인 대상이다.

## 발행과 확인

`Achievement`는 서버 전용 표다. `SpecFirestoreUploader`가 전용 DTO로 CSV를 읽고, 표 선택 목록과 콘텐츠 인덱스 발행에 포함한다. 클라이언트는 `getAchievements` 응답으로 정의를 받는다. 생성 테이블이나 `SpecData.bytes`에 업적을 추가하지 않는다.

로컬 구현만으로 기존 배포 서버에 기능이 생기지는 않는다. 현재 보상 구조 적용 시 서버 코드와 `Achievement`·`Title`·`Reward` 표 및 콘텐츠 인덱스를 함께 반영해야 한다. 클라이언트 UI와 Firestore 규칙의 적용 상태도 확인한다. 초기 구현 단계에서는 원격 업로드·배포 및 `SpecData.bytes` 재생성을 수행하지 않았다. 이후 서버 배포 상태는 아래 기록을 따른다.

새 서버는 이전 Achievement의 보상 열로 대체 지급하지 않는다. 업적 Reward 누락·미등록 칭호는 조회와 수령을 거절하므로 신구 서버와 스펙을 섞어 운영하지 않는다. 롤백할 때도 서버와 세 표가 포함된 이전 콘텐츠 인덱스를 함께 복원하고, 플레이어의 기존 수령 마커와 칭호 소유는 보존한다.

업적 도입 전 릴리스에는 이 표가 없으므로 롤백 검증은 기존 릴리스의 업적 표 누락을 허용한다. 새 릴리스를 발행할 때에는 다른 서버 표처럼 업적 표 업로드와 해시 일치를 확인한다. 제한된 보상 표 갱신용 `publish-local-spec.js`도 업적 CSV를 읽을 수 있지만, 신규 표의 최초 발행은 에디터의 정식 발행 경로를 사용한다.

오프라인 확인에는 CSV 스키마·고유 키·단계 순서·목표 증가·시너지 참조·달성 가능한 앨범 목표 검증과 서버 카탈로그 검증을 사용한다. CSV 이관 테스트와 서버 카탈로그 검증은 실제 CSV의 업적·칭호·Reward 참조, 지급물 종류·수량 및 중복 order를 검사한다. 실제 기기 화면과 배포 환경의 통합 동작은 별도 확인 대상이다.

2026-09-22 Reward 이관 검증: 단위 37개·Firestore 에뮬레이터 54개 통과. 재화 61행과 칭호 연결 8개 보존, 명시적 Reward 연결 변경, 미등록 칭호 거절, 순차·중복 수령과 원자적 롤백을 확인했다. TypeScript 빌드·변경 코드 ESLint·Unity 칭호 회귀·독립 C# 하네스 통과. CSV 발행 도구는 네트워크 없는 42개 검사에서 28개 표를 읽었으며 실제 발행은 하지 않았다. 보호 대상 bytes와 자동 생성 코드 2개는 변경하지 않았다.

2026-09-21 로컬 검증: 신규 업적 테스트 20개와 관련 회귀를 합친 서버 테스트 38개 통과. Firestore 에뮬레이터에서 중복·동시 수령, 영수증 만료 후 재청구, 트랜잭션 실패 시 취소, 구매·보상 팩 및 전투 정산 집계를 확인했다. TypeScript·Unity 런타임·에디터 코드 컴파일과 변경 서버 코드 린트가 통과했다. 클라이언트 실제 관리자 코드를 별도 실행한 15개 검사에서 단계 수령, 누적 진행, 오래된 응답 거부, 계정 초기화를 확인했고 신규 프리팹의 내부 참조도 검사했다. 실제 Unity 화면 플레이 검증은 수행하지 않았다.

2026-09-21 데이터 검증: 실제 C# 발행 파서와 CSV 파서로 310항목·61행을 확인했다. Node 발행 파서의 재화·스키마 오류 거절, 실제 시너지 8종 참조, 현재 앨범 목표 도달 가능 여부도 통과했다. 이 검증은 읽기 전용이며 시트·Firestore·생성 산출물을 변경하지 않았다.

## 서버 배포 완료 (2026-09-21)

사용자 지시에 따라 `bm-cardbattle` / `asia-northeast3`에 함수 11개를 배포했다: `getAchievements`, `claimAchievement`, `submitMatchResult`, `openPack`, `claimAttendance`, `claimMission`, `claimReward`, `claimPassReward`, `claimBattleExperience`, `spinRoulette`, `getOnboardingOperation`. `cardbattle` 데이터베이스의 Firestore 규칙도 배포했다. 이미 배포된 룰렛 순환 추첨 코드와 일치하는 소스를 사용했다.

배포 전 전체 린트·TypeScript 빌드·테이블 세대 일치 검사·규칙 컴파일 통과. 배포 후 11개 함수의 ACTIVE 상태와 신규 callable 2개의 인증 없는 요청 거절(401/UNAUTHENTICATED)을 확인했다. 작업 증거는 `Build/AchievementDeployment-20260921-164900/verification.json`에 있다.

조회 시점에 test/live 모두 `Achievement` 표와 인덱스 항목은 아직 없었다. 업적 적용용 업로드 대상은 `Achievement` 1개(61행)이며 별도 `Reward` 변경은 없다. Unity의 `Tools > Card Battle > 릴리즈 관리 > 데이터`에서 대상 환경과 `Achievement`를 선택하고, **업로드 후 공개 시리얼 올리기**를 켜서 **업로드 + 공개**한다. 업적만을 위해 테이블 세대를 올리거나 `SpecData.bytes`를 생성할 필요는 없다. 다른 미발행 표의 해시 차이로 공개가 거절되면 해당 표의 별도 변경을 확인한다.

이번 서버 배포에는 테이블 업로드·Hosting 리소스 배포·APK 빌드는 포함하지 않았다. 새 C# UI를 실행하려면 새 클라이언트 빌드가 필요하다. 실제 계정의 수령 및 기기 화면 검증은 테이블 발행과 클라이언트 반영 뒤에 수행한다.
